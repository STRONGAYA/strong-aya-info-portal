# STRONG AYA Information Portal
This repository contains the code for the basic version for the STRONG AYA information portal.  
The portal was designed in Adobe XD, and here is embedded in a GitHub pages application as a **proof of concept** 
that allows users to inspect data from multiple sources in a single interface.  
The repository has a Vantage6 integration
that attempts to retrieve the data from the STRONG AYA Vantage6 infrastructure.  
This integration is triggered through a GitHub workflow and will periodically repeat the task after a set interval.  
The proof of concept application is available at https://strongaya.github.io/strong-aya-info-portal/.

The full design of the portal is showcased in the `STRONG-AYA-Cancer-Info-Portal-Design.mp4` file
and is embedded below.

https://github.com/user-attachments/assets/154512a6-c9a5-49f8-bd9a-08ee88ba29f3

The portal is built using Adobe XD, Locofy.ai, GitHub Pages and Vantage6.  
A schematic overview can be found in the `STRONG-AYA-Info-Portal-PoC-Flow.svg` file and is embedded below.

## Data
Every topic page reads one small CSV with the number of people per category from `web/data/<variable>.csv`, e.g.
`web/data/ther_chemo.csv`:

```csv
category,count
received,1830
notReceived,1470
```

The counts are plain numbers of people (they do not have to add up to 100); the website scales them to
"out of 100 people" itself. The category names are the legend ids defined for the page in
`web/js/visualisation.js`. To replace the numbers shown on a page, edit or overwrite its CSV.

The treatment CSVs are regenerated by the `Update data through Vantage6 integration` workflow:
`scripts/vantage6_integration.py` stores the federated result in `data/raw/vantage6_result.json` and
`scripts/construct_counts.py` sums it into the categories listed in `data/variables.json`
(variable → category → raw values). The other CSVs are maintained by hand until the federated
analysis provides those variables as well.

The EORTC QLQ-AYA pages (e.g. `web/data/qlq_aya_sex_life.csv`) count people per answer: `notAtAll`, `aLittle`,
`quiteABit` and `veryMuch`, as the questions ask whether a part of life has been negatively affected. The answers
are scored like the EORTC QLQ-C30 (0–100, higher is more affected): a single question (romantic life, sex life) scores
0, 33, 67 or 100, and a scale (relationships, self-esteem) falls in the range of the nearest answer (0, up to 33,
up to 67, above 67). "Affected a lot" is quite a bit or very much. The QLQ-AYA has no published thresholds for
clinical importance yet: its international validation study runs until 2029.

### Articles from beatcancer.eu
The bottom of every topic page points to support and shows a few articles about the topic from
[beatcancer.eu](https://beatcancer.eu/resources/), the website of the European Youth Cancer Network (YARN);
they open in a new tab. That website has no API and cannot be embedded, so
`scripts/fetch_beatcancer_resources.py` reads its resource listing and writes the articles per page to
`web/data/beatcancer_resources.json`. The `Update beatcancer.eu resources` workflow does this every Monday and
redeploys the site when the articles changed; run it by hand from the Actions tab (or run the script locally) to
refresh them sooner:

```shell
python scripts/fetch_beatcancer_resources.py data/beatcancer_topics.json web/data/beatcancer_resources.json
```

Which articles a page shows is set in `data/beatcancer_topics.json`. Per page (the file name of the topic page):
- `topics`: the beatcancer.eu topics (as named in its topic filter) the page links to, and takes articles from
  when the keywords do not fill all places;
- `keywords`: groups of whole words or phrases; articles with a word of the first group in their title come first,
  then those of the next group, and so on (the newest first).

The article images come from beatcancer.eu's image service at 640 pixels wide (`image`). That service sometimes
fails to make this size of an image; the page then loads the 384-pixel version its own cards use (`image_fallback`)
instead, and leaves the image out if that fails too.

`exclude_types` and `exclude_title_words` skip articles that do not suit the pages (e.g. research papers, or
articles for caregivers or about the end of life), and `resources_per_page` sets the number of articles.

The titles, summaries, images and YARN logo belong to beatcancer.eu, which is run by Pagalbos onkologiniams ligoniams
asociacija (POLA), and the pages credit them as such. Its terms of use reserve all rights and ask for written
permission to reuse its content and logos, so agree this use with them (info@beatcancer.eu) before the portal is
published beyond testing.

### National websites for young people with cancer
When a visitor is in a European country that has a national website for young people with cancer, the first
beatcancer.eu card on a topic page makes way for a card for that website on the right, with a short heading of its
own (the beatcancer.eu heading then sits above the other two cards), and the support text names the website too, for example
[kanker.nl/jong](https://www.kanker.nl/jong) in the Netherlands. The websites are listed per country code in
`web/data/national_resources.json`:

```json
"NL": {
  "country": "Netherlands",
  "resources": [
    {"name": "Jong", "organisation": "kanker.nl", "url": "https://www.kanker.nl/jong", "lang": "nl",
     "description": "One sentence for a young reader about what the website offers.", "logo": "NL-nl.png"}
  ]
}
```

`lang` is the language of the website; when a country lists several websites (e.g. Belgium in Dutch and in
French), the one in the visitor's browser language is shown, else the first. `logo` names a file in
`web/images/national/` (or is `null`: then an illustration of the portal is shown); a logo drawn in white gets a
dark plate with `"logo_background": "#2d2d2d"`. The logos belong to the organisations: agree their use with them
before the portal is published beyond testing, as for beatcancer.eu. `confidence` and `notes` are for the
maintainers (how well the website fits young adults of 15 to 39, caveats) and are not shown; the websites that were
considered and rejected per country are in `data/national_resources_research.md`. Countries without an entry, and
visitors outside Europe, see the beatcancer.eu articles only.

The visitor's country is determined in the browser, without asking anything: from the browser language settings
(a country in a language tag such as `nl-BE`), then from the time zone (such as `Europe/Amsterdam`), then from a
language that is spoken mainly in one European country (such as `pl`). The **Country** button in the accessibility
bar opens a dialog in which the visitor can choose another country (or "Outside Europe"), or click **Use my
location**, and confirm with **Apply**. Only the location button makes the browser ask for permission to share the device position;
the coordinates are matched against the country outlines in `web/data/europe_countries.json` on the visitor's own
device and are not sent or stored by the portal (the browser itself may use a location service of its maker to find
the position). The topic pages never ask for the position on their own. A choice is kept for the visit only, in
`sessionStorage`: the country code and how it was found.

`web/data/europe_countries.json` holds simplified outlines of the European countries (Natural Earth, public
domain). `scripts/fetch_europe_countries.py` (standard library only) regenerates it and checks the result against
a list of European cities:

```shell
python scripts/fetch_europe_countries.py web/data/europe_countries.json
```

## Accessibility bar
The row of buttons under the purple banner holds the reader's own settings. **Contrast** and **Dark** change the
colours, **Size** opens a dialog with four text sizes (small at 85 %, normal, large at 115 % and extra large at
130 %: the stylesheet sizes all text and the widths of the content area in `rem`, so one root size scales the text
and widens the page, the tile, the figure and the notes with it, while the small icons keep their size),
**Language** and **Country** are described below. Contrast, dark mode and the text size are kept in
`localStorage` and put on the `<html>` element by `web/js/i18n.js` before the page is drawn, so they do not
flash. **Audio** (`web/js/read_aloud.js`) reads the main content of the page aloud with the browser's own speech
synthesis (the Web Speech API: no account, no server, nothing sent anywhere by the portal): the title, the
statement, the figure's spoken summary, the support text, the article titles and the info note, one sentence at a
time with the paragraph being read highlighted; a small bar under the buttons pauses, stops, skips a paragraph and
sets the speed (the only thing remembered), and a click on a paragraph starts from there. The voice comes from the
device, in the language of the page (or of a fragment with its own `lang`): installed voices first; when only an
online voice exists (Google's in Chrome, Microsoft's in Edge, where the text leaves the device) the visitor is asked
first, once per visit; when there is no voice for the language a dialog names the browser's own read-aloud feature
and how to add a voice. What it cannot do, and why, is in `docs/plan_audio_read_aloud.md`: the voices are the
device's (Windows has only legacy voices for Dutch, Italian, Polish and Romanian, iOS hides its best ones from web
pages, Linux often has none), highlighting is per paragraph, and phones stop speaking when the screen locks. If
the device voices prove too poor for a language, section 5.1 of that plan describes the second step: audio files
generated at build time from the translation cache with Mistral's Voxtral text-to-speech on its EU endpoint (the
only provider allowed outside the browser), played by the same controls, with the browser voice as the fallback.

## Languages
English is the only language that is written by hand. The portal is translated at build time with
[DeepL](https://www.deepl.com/pro-api), never in the browser: `scripts/translate_site.py` (standard library only)
writes one static page tree per language (`web/nl/module_a/chemotherapy.html`, ...) plus one strings file per
language (`web/i18n/nl.js`) for the text the scripts generate (glossary, help, dialogs, legends, table and chart
labels, the beatcancer.eu block, the national website card). These files are generated output, committed like
`web/data/beatcancer_resources.json`: do not edit them, edit the English page or the translation cache instead.
A language costs about 31,000 DeepL characters once (about €0.70 at €22 per million on the paid plans; text sent
to the paid API is not stored or used for training), then only the changed sentences. DeepL's glossaries are
not available for Croatian, Irish, Maltese and a few other languages, and the formality setting only exists for
German, French, Italian, Spanish, Dutch, Polish and Portuguese; the script applies both where they exist.

### How the pages are translated
- The English sources are the 17 pages in `web/` and `web/i18n/en.js`. In the pages, a translation unit is the
  inner HTML of a block element (title, headings, paragraphs, list items, buttons, links that stand on their own)
  plus the attributes that are read out (`alt`, `aria-label`, `title`, `placeholder`, `data-tooltip`), so links,
  bold words and hidden notes inside a sentence stay where they are. Elements marked `translate="no"` (the
  e-mail address, phone number, address and logos) and text in another language (`lang="nl"` on a national
  website's name) are left as they are. In `en.js`, every string is a unit; `{name}` placeholders are protected.
  The one-sentence descriptions of the national websites (`web/data/national_resources.json`) are units too:
  they land in the strings file of a language under `national.descriptions`, keyed by country code and
  position (`"NL/0"`), and the card shows that text instead of the English one.
- Every unit is cached in `translations/<lang>.json` under the SHA-256 of its English text, with the DeepL result,
  a `status` (`machine` or `reviewed`), the glossary version and the billed characters. The same sentence on all
  17 pages is one entry; unchanged text is never sent to DeepL again, and a `reviewed` entry is never overwritten.
  A changed English sentence is a new entry (the old one becomes an orphan that `--prune` lists).
- Terms that must stay the same (STRONG-AYA, AYA, HADS, EORTC QLQ-C30, ...) and terms the reviewers want
  translated in a fixed way are in `translations/glossary.tsv` (one column per language, `*` for "the same in every
  language"); `--sync-glossary` uploads it as one DeepL glossary. DeepL's settings (the next-generation model,
  informal address, plain-language instructions, the context sentence) are in `translations/config.json`.
- A generated page gets `<html lang="nl" data-translation="machine|reviewed">`, asset paths one level deeper,
  `hreflang` links to the same page in every language (also kept up to date in the English pages, between the
  `hreflang:start` and `hreflang:end` comments), and a notice under the purple banner that says the page was
  translated automatically (or by whom it was checked), with a link to the English page. `web/i18n/languages.js`
  lists the languages that exist, with their status, for the language switcher.

```shell
export DEEPL_AUTH_KEY=...                                 # a DeepL API key (ending in :fx on the free plan)
python scripts/translate_site.py --languages nl --dry-run  # what a run would send to DeepL (characters per language)
python scripts/translate_site.py --languages nl            # translate the cache misses and write web/nl/, web/i18n/nl.js
python scripts/translate_site.py --check                   # no key needed: are the generated files up to date and untouched?
python scripts/translate_site.py --export-review nl        # translations/review/nl.csv for a reviewer; --import-review nl reads it back
```

A language is enabled by the existence of its cache file: the first `--languages nl` run with the key creates
`translations/nl.json`; later runs without `--languages` cover every language that has one. **Without a DeepL
key** the script does not call the API: it regenerates the pages of the languages whose text is fully cached and
leaves the others as they are, and the visitors of a language the portal does not have can translate the English
pages with their browser (see below). Reviewing happens in the pull request or in the exported CSV: change
`target`, set `status` to `reviewed` and name yourself in `reviewer`; the pages are regenerated from the cache.
Named reviewers and the month of the review per language go in `translations/config.json` under `languages`, for
the notice on the pages.

The `Translate the portal` workflow (`.github/workflows/translate_site.yml`) runs the script on GitHub: by hand
from the Actions tab (with the languages to add and the mode), and after every push to `main` that changes `web/**`
or `translations/**`. It needs the repository secret `DEEPL_AUTH_KEY`; the key exists only inside the job, and the
cache holds text only. New machine translations are opened as a pull request on a `translations/<date>` branch for
review; when only already-cached text was regenerated, the workflow commits directly and redeploys the site. On
pull requests, a second job runs `--check` without the key, so that hand edits of generated files are noticed
(GitHub does not run `pull_request` workflows for a pull request that a workflow opened with its own token, so
the review pull requests are regenerated by the translate job on every push to their branch instead).
`scripts/test_translate_site.py` tests the extractor, the page generation and the checks against the real pages.

### Choosing a language in the browser
`web/js/i18n.js` is loaded first on every page. A visitor who opens an English page is sent to the same page in
the first language of their browser settings that the portal has (`nl-BE` counts as `nl`); a page in another
language that a visitor opens directly (a shared link) is shown as it is. The **Language** button in the
accessibility bar lists the languages with their status (original, translated automatically, checked by a
person); a choice made there, or `?lang=nl` in the address (for links in a newsletter), is kept in `localStorage`
like the contrast and dark modes, and followed on every page from then on. English is never implied by a country,
and a country never by a language: the **Country** choice for the national website is separate.

When the portal does not have the visitor's language, the browser can translate the page itself. In Chrome and
Edge 138 or later the Language dialog offers **Translate with your browser**: the [Translator
API](https://developer.mozilla.org/en-US/docs/Web/API/Translator_and_Language_Detector_APIs) translates the text
of the page on the device with a language model the browser downloads once (the portal sends nothing anywhere for
it), the text the scripts add later (dialogs, the figure, the article cards) included; that choice is remembered
and applied again on the next page, and the notice under the banner says the browser made the translation. Other
browsers get a short explanation of their own translate feature (the address bar or the right-click menu); the
pages carry `lang` and `translate="no"` where needed so that those features work well, and the notice is shown
when Chrome's own feature has translated the page. The text that the scripts generate is in `web/i18n/en.js`;
`t('group.key', { name: value })` reads it, with `{name}` placeholders and, for entries with `one`/`other` forms,
the plural rules of the page language.

The beatcancer.eu articles stay in English on the pages in other languages (the linked articles are English, and
beatcancer.eu's terms reserve all rights); their titles are marked `lang="en"` and a note says so. Dutch comes
first (reviewers at NKI, Maastricht and IKNL), then the consortium languages; Greek, Bulgarian and Ukrainian also
need a font with those scripts, as Poppins has no Greek or Cyrillic subset (Noto Sans, self-hosted with
`unicode-range` like Poppins, would cover them).

## Prequisites for own application
- ### When using the descriptive statistics algorithm (default)
  - Vantage6 server and collaboration with nodes running on version 4.x.x
  - Distributed data in RDF-triple format 
  (produced using the Triplifier tool e.g. through https://github.com/MaastrichtU-CDS/Flyover)
  - Annotated data using the SIO's has-attribute relation 
  (http://semanticscience.org/resource/SIO_000008)
  - GraphDB instances running and accessible on distributed data stations
  - Credentials to send a task to the Vantage6 server stored as GitHub secrets
- ### In development mode
  - Python 3.10 environment with libraries in `requirements.txt` installed
  - Access to example data in `example_data/` or alternative data in the same format
